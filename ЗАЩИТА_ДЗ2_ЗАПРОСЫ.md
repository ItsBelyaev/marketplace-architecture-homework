## 8. Демонстрация refresh token

```bash
curl -sS -i -X POST http://localhost:8080/auth/refresh \
  -H 'Content-Type: application/json' \
  -d "{\"refresh_token\":\"$BUYER_REFRESH\"}"
```

Ожидается `200 OK` и новая пара токенов.

Важно: для дальнейших запросов можно продолжить использовать старый access token, потому что он ещё не истёк.

Что сказать:

> Refresh token нельзя использовать вместо access token. Внутри JWT есть claim `type`, и сервер отдельно проверяет тип токена.

```bash
echo "$ORDER_RESPONSE" | jq
```

Сохранить UUID заказа:

```bash
ORDER_ID=$(echo "$ORDER_RESPONSE" | jq -r '.id')
echo "ORDER_ID=$ORDER_ID"
```

Ожидаемый смысл ответа:

```json
{
  "status": "CREATED",
  "promo_code": "SALE...",
  "total_amount": 180.00,
  "discount_amount": 20.00,
  "items": [
    {
      "quantity": 2,
      "price_at_order": 100.00
    }
  ]
}
```

Расчёт:

```text
2 × 100 = 200
скидка 10% = 20
итог = 180
```

Что сказать:

> Создание заказа и уменьшение остатков находятся в одной транзакции. Товар блокируется через SELECT FOR UPDATE. Если любая проверка завершится ошибкой, все изменения откатятся.

## 16. Демонстрация price snapshot

Сначала изменить текущую цену товара со 100 на 150. Остаток сейчас равен 8, поэтому при обновлении передаём `stock: 8`.

```bash
curl -sS -X PUT "http://localhost:8080/products/$PRODUCT_ID" \
  -H "Authorization: Bearer $SELLER_TOKEN" \
  -H 'Content-Type: application/json' \

    "price":150.00,
    "stock":8,
    "category":"Электроника",
```

```bash
  -H "Authorization: Bearer $BUYER_TOKEN" \

```

Должно быть:

- текущая цена товара — `150`;
- `price_at_order` в заказе — `100`;
- `total_amount` старого заказа — `180`.

Что сказать:

> В позиции заказа сохраняется снимок цены. Изменение каталога не должно задним числом менять уже оформленный заказ.

## 18. Ошибка недостаточного остатка

Второй покупатель пытается заказать 999 единиц, хотя доступно только 8:

```text

```

В `details` должны быть:

- `product_id`;
- `requested: 999`;

Остаток должен по-прежнему быть `8`.

Что сказать:

> Проверка завершилась ошибкой до фиксации транзакции, поэтому остаток не изменился и частичный заказ не появился.

## 26. Демонстрация rate limit

Сразу после отмены основной покупатель пытается создать новый заказ:

```bash
curl -sS -i -X POST http://localhost:8080/orders \
  -H "Authorization: Bearer $BUYER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{
    \"items\":[
      {
        \"product_id\":\"$PRODUCT_ID\",
        \"quantity\":1
      }
    ]
  }"
```

Если с первого создания прошло меньше минуты, ожидается:

```text
HTTP/1.1 429
ORDER_LIMIT_EXCEEDED
```

В `details` будут лимит и время последней операции.

Если прошло больше минуты, заказ может успешно создаться. В таком случае этот сценарий лучше не показывать либо заранее поставить больший `ORDER_LIMIT_MINUTES`.

## 35. Что говорить во время основного сценария

Короткий текст:
