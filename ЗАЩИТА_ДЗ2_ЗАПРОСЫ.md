

Что происходит внутри:

3. Maven запускает OpenAPI Generator и компилирует Java-приложение.

5. Только после готовности PostgreSQL запускается Spring Boot.
6. Flyway подключается к базе и применяет миграцию `V1__init.sql`.
7. Docker начинает проверять endpoint `/health` приложения.

Что этим доказываем:

- проект воспроизводимо собирается;
- приложение действительно работает в Docker;
- PostgreSQL также запускается в Docker;
- приложение умеет дождаться готовности базы;
- OpenAPI-кодогенерация встроена в обычную сборку.

Если преподаватель спросит, зачем два контейнера:

> Приложение и база — разные процессы с разным жизненным циклом. Docker Compose связывает их общей сетью, но не смешивает в одном образе.

Если спросит, почему база доступна на `5433`, а не `5432`:

> Внутри контейнера PostgreSQL слушает стандартный порт 5432. На компьютере он опубликован как 5433, чтобы не конфликтовать с локальным PostgreSQL.

## Минимум 4. Регистрация продавца и покупателя

Продавец:

```bash
curl -sS -X POST http://localhost:8080/auth/register \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"$SELLER_USERNAME\",\"password\":\"$PASSWORD\",\"role\":\"SELLER\"}" | jq
```

Покупатель:

```bash
curl -sS -X POST http://localhost:8080/auth/register \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"$BUYER_USERNAME\",\"password\":\"$PASSWORD\",\"role\":\"USER\"}" | jq
```

Сказать:

> Пароль сохраняется не открытым текстом, а как BCrypt-хеш. SELLER управляет товарами, USER работает с заказами.

Что происходит внутри регистрации:

1. Сгенерированный DTO проверяет обязательные поля, длину логина и пароля и значение роли.
2. `AuthService` ищет пользователя с таким логином.
3. Если логин свободен, BCrypt создаёт хеш пароля.
4. `UserRepository` записывает пользователя в таблицу `users`.
5. `JwtService` сразу выдаёт access и refresh tokens.

Почему регистрируем две роли:

- `SELLER` понадобится для создания товара и промокода;
- `USER` понадобится для создания заказа;
- так мы сразу демонстрируем ролевую модель из задания.

Что этим доказываем:

- работают `POST /auth/register` и PostgreSQL;
- пароль не хранится открытым текстом;
- роли существуют не только в документации, но и реально влияют на доступ;
- ответы соответствуют схемам OpenAPI.

Если преподаватель спросит, почему пользователь сам передаёт роль при регистрации:

> Это учебное упрощение для демонстрации всех ролей. В production роль продавца или администратора обычно выдаётся отдельным доверенным процессом.

## Минимум 5. Вход и сохранение токенов

```bash
SELLER_TOKEN=$(curl -sS -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"$SELLER_USERNAME\",\"password\":\"$PASSWORD\"}" \
  | jq -r '.access_token')
```

```bash
BUYER_TOKEN=$(curl -sS -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"$BUYER_USERNAME\",\"password\":\"$PASSWORD\"}" \
  | jq -r '.access_token')
```

Проверить, что токены получены:

```bash
echo "SELLER token length: ${#SELLER_TOKEN}"
echo "BUYER token length: ${#BUYER_TOKEN}"
```

Сказать:

> Access token передаётся в заголовке Authorization. Он содержит UUID пользователя и роль и живёт 20 минут.

Что происходит внутри входа:

1. `AuthService` находит пользователя по логину.
2. BCrypt сравнивает переданный пароль с хешем из базы.
3. `JwtService` подписывает access и refresh tokens секретом HMAC SHA-256.
4. `jq -r '.access_token'` достаёт access token из JSON без кавычек.
5. Конструкция `$(...)` сохраняет токен в переменную shell.

Почему выводим только длину:

> Полный JWT очень длинный. Длина больше нуля подтверждает, что токен получен, но не засоряет экран. В следующих запросах он действительно используется.

Что записано в access token:

- `sub` — UUID пользователя;
- `username` — логин;
- `role` — роль;
- `type=access`;
- время выдачи и окончания;
- issuer `marketplace`.

Что этим доказываем:

- работает `POST /auth/login`;
- сервер проверяет пароль;
- JWT реально используется для защищённых endpoints;
- продавец и покупатель получают токены с разными ролями.

Если спросят про refresh token:

> Он живёт 14 дней и используется только в `/auth/refresh`. Внутри есть `type=refresh`, поэтому его нельзя использовать как access token.

```bash
PRODUCT_RESPONSE=$(curl -sS -X POST http://localhost:8080/products \
  -H "Authorization: Bearer $SELLER_TOKEN" \
  -H 'Content-Type: application/json' \

```

```bash
echo "$PRODUCT_RESPONSE" | jq
```

Показать цену `100`, остаток `10`, статус `ACTIVE` и `seller_id`.

> seller_id сервер берёт из JWT. Продавец сможет изменять только собственный товар.

Что происходит внутри:

1. `JwtAuthenticationFilter` проверяет подпись access token.

3. `ProductService` разрешает операцию только `SELLER` или `ADMIN`.

6. PostgreSQL автоматически заполняет `created_at` и `updated_at`.

Зачем сохраняем весь ответ в `PRODUCT_RESPONSE`:

> Из ответа нужно автоматически достать UUID товара. Затем этот UUID используется в заказе и SQL-запросах. Так не приходится копировать его руками.

Что проверяет валидация ещё до Service:

- название обязательно и не длиннее 255 символов;
- цена не меньше `0.01`;
- stock неотрицательный;
- категория обязательна;
- статус должен быть `ACTIVE`, `INACTIVE` или `ARCHIVED`.

Что этим доказываем:

- работает `POST /products`;
- JWT-аутентификация действительно определяет продавца;
- generated DTO используется в приложении;
- товар реально связан со своим владельцем.

Что означает каждое поле:

2. Создавать промокод может `SELLER` или `ADMIN`.

4. Репозиторий записывает промокод с `current_uses=0`.

Что этим доказываем:

- промокоды существуют как отдельная сущность в базе;
- ограничения промокода будут проверены внутри транзакции заказа;
- ролевой доступ действует не только для товаров.

## Минимум 8. Покупатель создаёт заказ

```bash
ORDER_RESPONSE=$(curl -sS -X POST http://localhost:8080/orders \
  -H "Authorization: Bearer $BUYER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"items\":[{\"product_id\":\"$PRODUCT_ID\",\"quantity\":2}],\"promo_code\":\"$PROMO_CODE\"}")
```

```bash
echo "$ORDER_RESPONSE" | jq
ORDER_ID=$(echo "$ORDER_RESPONSE" | jq -r '.id')
```

Показать:

- `status: CREATED`;
- `price_at_order: 100`;
- `discount_amount: 20`;
- `total_amount: 180`.

Расчёт:

```text
2 × 100 = 200
скидка 10% = 20
итог = 180
```

Сказать:

> Создание заказа и резервирование остатка выполняются в одной транзакции. Товар блокируется через SELECT FOR UPDATE. При ошибке изменения откатываются.

Что происходит внутри `OrderService.create`:

1. Проверяется, что роль — `USER` или `ADMIN`. Продавец создавать заказ не может.
2. Проверяется время последней операции `CREATE_ORDER`.
3. Проверяется отсутствие другого активного заказа пользователя.
4. Проверяется, что один товар не продублирован в массиве.
5. Товар загружается через `SELECT ... FOR UPDATE`.
6. Проверяются существование товара и статус `ACTIVE`.
7. Проверяется `stock >= quantity`.
8. Считается subtotal: `100 × 2 = 200`.
9. Промокод также блокируется и проверяется: активность, срок, лимит и минимальная сумма.
10. Рассчитывается скидка `200 × 10% = 20`.
11. Stock уменьшается на две единицы.
12. Создаются `orders` и `order_items`.
13. В `order_items.price_at_order` сохраняется цена `100`.
14. `current_uses` промокода увеличивается до одного.
15. В `user_operations` записывается операция для rate limit.
16. Транзакция делает commit.

Почему важен `@Transactional`:

> Все изменения составляют одну операцию. Если, например, заказ не сохранится после уменьшения stock, Spring выполнит rollback и вернёт stock обратно.

Почему важен `FOR UPDATE`:

> Без блокировки два параллельных запроса могли бы одновременно увидеть одинаковый остаток и продать больше товара, чем есть на складе.

Почему существует `price_at_order`:

> Это исторический снимок цены. Последующее изменение цены товара не должно менять старый заказ.

Что этим доказываем:

- реализована сложная бизнес-логика пункта 7;
- работают транзакции, остатки и промокоды;
- итоговая сумма считается сервером, а не приходит готовой от клиента;
- заказ связан с текущим пользователем из JWT.

## Минимум 9. Проверка остатка

```bash
curl -sS "http://localhost:8080/products/$PRODUCT_ID" \
  -H "Authorization: Bearer $BUYER_TOKEN" \
  | jq '{id, price, stock, status}'
```

Показать, что `stock` уменьшился с `10` до `8`.

Сказать:

> Две единицы зарезервированы заказом, поэтому осталось восемь.

Почему нужен отдельный `GET` после заказа:

> Ответ создания заказа показывает сам заказ, но не доказывает изменение каталога. Повторное чтение товара показывает результат резервирования через API.

Что происходит:

- до заказа `stock=10`;
- заказ содержит `quantity=2`;
- внутри транзакции выполнено `stock = stock - 2`;
- после commit новый запрос читает `stock=8`.

Что этим доказываем:

- бизнес-логика действительно изменила связанные данные;
- транзакция успешно завершилась;
- покупатель может читать каталог, но не изменяет stock напрямую.

Если преподаватель спросит, что будет при недостаточном остатке:

> Сервер соберёт список проблемных товаров и вернёт `409 INSUFFICIENT_STOCK` с requested и available. Заказ не создастся, stock не изменится.

## Минимум 10. Обязательные SELECT из базы

В условии прямо сказано показать содержимое таблиц через `SELECT`.

Товар:

```bash
docker compose exec -T db psql -U marketplace -d marketplace -c \
  "SELECT id, name, price, stock, status FROM products WHERE id = '$PRODUCT_ID';"
```

Заказ:

```bash
docker compose exec -T db psql -U marketplace -d marketplace -c \
  "SELECT id, user_id, status, total_amount, discount_amount FROM orders WHERE id = '$ORDER_ID';"
```

Позиция заказа:

```bash
docker compose exec -T db psql -U marketplace -d marketplace -c \
  "SELECT order_id, product_id, quantity, price_at_order FROM order_items WHERE order_id = '$ORDER_ID';"
```

Этих трёх `SELECT` для основного показа достаточно.

Сказать:

> Я показываю не только ответ API, но и реальные записи в PostgreSQL. В order_items отдельно сохранена цена на момент заказа.

Зачем нужны три таблицы:

- `products` подтверждает текущую цену, статус и уменьшенный stock;
- `orders` подтверждает владельца, статус, итог и скидку;
- `order_items` подтверждает связь заказа с товаром, количество и `price_at_order`.

Почему это обязательно:

> В условии защиты прямо сказано выполнить `SELECT` и показать содержимое таблиц. Одного JSON-ответа API недостаточно.

Что означает `docker compose exec -T db`:

- `exec` запускает команду внутри уже работающего контейнера базы;
- `-T` отключает интерактивный терминал, поэтому результат сразу печатается;
- `psql -U marketplace -d marketplace` подключается к нужной базе;
- `-c` выполняет один SQL-запрос и завершает работу.

На что обратить внимание преподавателя:

- UUID в `products.id` совпадает с `order_items.product_id`;
- UUID заказа совпадает с `order_items.order_id`;
- `stock=8`;
- `quantity=2`;
- `price_at_order=100`;
- `total_amount=180`, `discount_amount=20`.

Что этим доказываем:

- API не возвращает выдуманный ответ: данные действительно сохранены;
- foreign key-связи работают;
- цена сохранена отдельно от текущей цены товара;
- числовые значения согласованы между таблицами.

## Минимум 11. Одна ошибка валидации

```bash
curl -sS -i -X POST http://localhost:8080/products \
  -H "Authorization: Bearer $SELLER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Ошибка","price":-1,"stock":0,"category":"Тест","status":"ACTIVE"}'
```

Показать:

```text
HTTP/1.1 400
VALIDATION_ERROR
```

Сказать:

> Минимальная цена задана в OpenAPI. Невалидный запрос останавливается Bean Validation до бизнес-логики.

Почему отправляем именно отрицательную цену:

- ограничение легко увидеть;
- OpenAPI содержит `minimum: 0.01`;
- ответ должен перечислить конкретное поле `price`;
- товар не должен появиться в базе.

Что происходит внутри:

1. JSON преобразуется в сгенерированный `ProductCreate`.
2. Bean Validation видит нарушение `price >= 0.01`.
3. Метод `ProductService.create` не вызывается.
4. `GlobalExceptionHandler` формирует единый `ErrorResponse`.

Что нужно показать в ответе:

- HTTP `400`;
- `error_code=VALIDATION_ERROR`;
- `message`;
- `details.fields` с полем `price` и причиной ошибки.

Что этим доказываем:

- ограничения из OpenAPI реально применяются;
- невалидные данные не доходят до SQL;
- ошибки соответствуют единому контракту.

Второй покупатель пытается заказать 999 единиц, хотя доступно только 8:

```bash
curl -sS -i -X POST http://localhost:8080/orders \
  -H "Authorization: Bearer $BUYER2_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{
    \"items\":[
      {
        \"product_id\":\"$PRODUCT_ID\",
        \"quantity\":999
      }
    ]
  }"
```

Ожидается:

```text
HTTP/1.1 409
INSUFFICIENT_STOCK
```

В `details` должны быть:

- `product_id`;
- `requested: 999`;
- `available: 8`.

Проверить, что неуспешный заказ не изменил stock:

```bash
curl -sS "http://localhost:8080/products/$PRODUCT_ID" \
  -H "Authorization: Bearer $BUYER2_TOKEN" | jq '{stock}'
```

Остаток должен по-прежнему быть `8`.

Что сказать:

> Проверка завершилась ошибкой до фиксации транзакции, поэтому остаток не изменился и частичный заказ не появился.

## 19. Ошибка валидации

Продавец пытается создать товар с отрицательной ценой:

```bash
curl -sS -i -X POST http://localhost:8080/products \
  -H "Authorization: Bearer $SELLER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "name":"Неверный товар",
    "price":-1,
    "stock":0,
    "category":"Тест",
    "status":"ACTIVE"
  }'
```

Ожидается:

```text
HTTP/1.1 400
VALIDATION_ERROR
```

В `details.fields` будет поле `price` и сообщение о минимальном значении `0.01`.

Что сказать:

> Ограничение цены задано в OpenAPI. Оно попадает в сгенерированный DTO как Bean Validation-аннотация, поэтому невалидный запрос не доходит до бизнес-логики.

```bash

```

Ожидается:

```bash
  -H "Authorization: Bearer $BUYER_TOKEN" \
```

> Отмена выполняется транзакционно. Она возвращает остатки, уменьшает использование промокода и меняет статус заказа.

## 26. Демонстрация rate limit

Сразу после отмены основной покупатель пытается создать новый заказ:

```bash
curl -sS -i -X POST http://localhost:8080/orders \
  -H "Authorization: Bearer $BUYER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{
    \"items\":[
      {
        \"product_id\":\"$PRODUCT_ID\",
        \"quantity\":1
      }
    ]
  }"
```

Если с первого создания прошло меньше минуты, ожидается:

```text
HTTP/1.1 429
ORDER_LIMIT_EXCEEDED
```

В `details` будут лимит и время последней операции.

Если прошло больше минуты, заказ может успешно создаться. В таком случае этот сценарий лучше не показывать либо заранее поставить больший `ORDER_LIMIT_MINUTES`.

## 35. Что говорить во время основного сценария

Короткий текст:

> Сначала я запускаю Java-приложение и PostgreSQL через Docker Compose. Health-check отвечает 200 и возвращает request id.
>
> Регистрирую продавца и покупателя. Пароли хранятся как BCrypt-хеши, после входа сервер выдаёт access и refresh tokens.
>
> Продавец создаёт товар с ценой 100 и остатком 10. Обычный пользователь создавать товары не может.
>
> Затем продавец создаёт процентный промокод на 10%. Покупатель оформляет две единицы товара. Сумма до скидки 200, скидка 20, итог 180.
>
> Создание заказа и резервирование товара выполняются в одной транзакции. Товар блокируется через SELECT FOR UPDATE. После заказа остаток уменьшается с 10 до 8.
>
> Я показываю данные непосредственно в PostgreSQL: заказ, позицию с price_at_order и запись пользовательской операции.
>
> Затем меняю текущую цену товара на 150. В старом заказе price_at_order остаётся 100, то есть история не меняется.
>
> При отмене заказа stock возвращается до 10, использование промокода уменьшается, а статус становится CANCELED.
>
> Ошибки имеют единый формат error_code, message, details. Каждый запрос записывается в JSON-лог, а пароль и токены маскируются.

## 39. Диагностика проблем

### Проверить контейнеры

```bash
docker compose ps
```

### Логи приложения

```bash
docker compose logs app --tail=100
```

### Логи базы

```bash
docker compose logs db --tail=100
```

### Проверить health

```bash
curl -v http://localhost:8080/health
```

### Проверить подключение к PostgreSQL

```bash
docker compose exec -T db pg_isready -U marketplace -d marketplace
```

### Если `jq: command not found`

Без `jq` можно выполнять запросы, но автоматическое получение UUID и токенов не сработает. Тогда скопируй значения вручную из JSON. На macOS `jq` можно установить заранее, но во время защиты лучше уже иметь его установленным.

### Если переменная оказалась пустой

Проверить:

```bash
echo "$PRODUCT_ID"
echo "$ORDER_ID"
echo "${#SELLER_TOKEN}"
echo "${#BUYER_TOKEN}"
```

Чаще всего причина — команда выполнена в другом терминале или предыдущий запрос вернул ошибку.

### Если пользователь уже существует

Повторно выполнить блок переменных:

```bash
RUN_ID=$(date +%s)
SELLER_USERNAME="seller_$RUN_ID"
BUYER_USERNAME="buyer_$RUN_ID"
BUYER2_USERNAME="buyer2_$RUN_ID"
PROMO_CODE="SALE$(date +%H%M%S)"
```

После этого повторить регистрацию и вход.
