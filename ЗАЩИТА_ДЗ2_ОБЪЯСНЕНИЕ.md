# Защита ДЗ2: полное объяснение проекта человеческим языком

Этот файл нужен для устной части защиты. Его не надо учить дословно. Сначала прочитай разделы 1–6, затем готовую речь и вопросы в конце.

---

## 1. Что вообще сделано

Сделан backend учебного маркетплейса. Backend — это серверная часть без красивого сайта. Пользователь или Swagger отправляет серверу HTTP-запрос, сервер проверяет данные и права, выполняет нужное действие и возвращает JSON.

Проект умеет:

- регистрировать пользователей;
- выполнять вход по логину и паролю;
- выдавать access token и refresh token;
- различать роли `USER`, `SELLER`, `ADMIN`;
- создавать, получать, изменять и архивировать товары;
- получать список товаров с пагинацией и фильтрацией;
- создавать промокоды;
- создавать, получать, изменять и отменять заказы;
- проверять наличие товаров и остатки;
- резервировать товар при создании заказа;
- возвращать товар на склад при отмене;
- сохранять цену, по которой товар был куплен;
- считать процентную или фиксированную скидку;
- запрещать слишком частые операции с заказами;
- возвращать ошибки в одном формате;
- записывать каждый HTTP-запрос в JSON-лог;
- запускаться вместе с PostgreSQL через Docker Compose.

Главная идея проекта: API сначала полностью описано в OpenAPI, а затем часть Java-кода автоматически генерируется из этого описания. Такой подход называется contract-first.

## 2. Самое простое объяснение архитектуры

Запрос проходит через несколько слоёв:

```text
Пользователь или Swagger
        ↓
HTTP-запрос
        ↓
Logging Filter — записывает информацию о запросе
        ↓
JWT Filter — проверяет токен и определяет пользователя
        ↓
Сгенерированный Controller — принимает запрос по контракту OpenAPI
        ↓
Delegate — тонкая прослойка, передаёт запрос дальше
        ↓
Service — выполняет бизнес-правила
        ↓
Repository — выполняет SQL-запросы
        ↓
PostgreSQL — хранит данные
        ↓
JSON-ответ пользователю
```

Простая аналогия с магазином:

- OpenAPI — правила магазина и список доступных услуг;
- Controller — окно приёма заявок;
- Delegate — сотрудник, который передаёт заявку нужному отделу;
- Service — менеджер, принимающий бизнес-решения;
- Repository — сотрудник архива, который читает и записывает данные;
- PostgreSQL — архив или склад данных;
- Docker — коробка, в которой приложение одинаково запускается на разных компьютерах.

## 3. Термины, которые могут спросить

### API

Набор адресов и правил, по которым внешняя программа общается с сервером. Например, `POST /products` создаёт товар, а `GET /products/{id}` получает товар.

### Endpoint

Конкретная комбинация HTTP-метода и адреса. Например:

```text
POST /orders
```

### JSON

Текстовый формат передачи данных. Пример товара:

```json
{
  "name": "Наушники",
  "price": 100,
  "stock": 10
}
```

### OpenAPI

Формальное описание API в YAML-файле. В нём написано, какие запросы существуют, какие поля обязательны, какие ответы и ошибки возможны.

### Contract-first

Сначала создаётся контракт `api.yaml`, а уже потом реализация. Клиент и сервер заранее знают, в каком формате общаться.

### DTO

Объект для передачи данных через API. Например, `ProductCreate` — данные для создания товара, а `ProductResponse` — ответ с товаром. В этом проекте DTO генерируются из OpenAPI, вручную они не написаны.

### CRUD

Четыре базовые операции с сущностью:

- Create — создать;
- Read — прочитать;
- Update — изменить;
- Delete — удалить.

В проекте удаление товара мягкое: строка не удаляется физически, статус становится `ARCHIVED`.

### PostgreSQL

Реляционная база данных. Она хранит пользователей, товары, заказы, позиции заказов, промокоды и историю операций.

### Flyway

Инструмент миграций базы. При запуске приложения он смотрит, какие версии схемы уже применены, и выполняет новые SQL-файлы по порядку.

### JWT

Подписанный токен, подтверждающий личность и роль пользователя. Пользователь передаёт access token в заголовке `Authorization`.

### Транзакция

Группа изменений, которая выполняется целиком. Либо применяются все изменения, либо при ошибке отменяются все.

### `SELECT FOR UPDATE`

SQL-блокировка выбранных строк. Пока один заказ работает с остатком товара, второй заказ не может одновременно изменить ту же строку.

### Пагинация

Выдача данных частями. Например, `page=0&size=20` означает первую страницу из 20 товаров.

### Rate limit

Ограничение частоты операций. В проекте пользователь не может слишком часто создавать или изменять заказ.

### Dependency Injection

Spring сам создаёт объекты и передаёт их друг другу через конструкторы. Например, `OrderService` получает готовые репозитории, а не создаёт их через `new`.

## 4. Основные сценарии

### Регистрация и вход

1. Пользователь отправляет логин, пароль и роль.
2. `AuthService` проверяет, что логин не занят.
3. Пароль преобразуется в BCrypt-хеш.
4. Пользователь записывается в таблицу `users`.
5. Сервер выдаёт access и refresh tokens.

При входе сервер находит пользователя, сравнивает пароль с BCrypt-хешем и выдаёт новую пару токенов.

### Создание товара

1. JWT-фильтр определяет пользователя.
2. `ProductService` проверяет роль.
3. Создавать товар может `SELLER` или `ADMIN`.
4. UUID продавца сохраняется в `seller_id`.
5. Товар записывается в PostgreSQL.

Обычный `USER` создать товар не может.

### Изменение товара

Продавец может менять только товар, у которого `seller_id` совпадает с его UUID. Администратор может менять любой товар.

### Архивирование товара

`DELETE /products/{id}` не удаляет строку. Репозиторий выполняет примерно такое действие:

```sql
UPDATE products SET status = 'ARCHIVED' WHERE id = ...;
```

История сохраняется, а товар становится недоступен для новых заказов.

### Создание заказа

Самый важный сценарий находится в `OrderService.create`.

Порядок действий:

1. Проверяется, что запрос выполняет `USER` или `ADMIN`.
2. Проверяется rate limit создания заказа.
3. Проверяется отсутствие другого активного заказа.
4. Повторяющиеся товары в массиве запрещаются.
5. Товары загружаются из базы с блокировкой `FOR UPDATE`.
6. Проверяется существование каждого товара.
7. Проверяется статус `ACTIVE`.
8. Проверяется достаточность остатка.
9. Рассчитывается сумма без скидки.
10. Проверяется промокод, если он передан.
11. Уменьшается `stock` каждого товара.
12. Создаётся запись в `orders`.
13. Создаются записи в `order_items`.
14. Увеличивается `current_uses` промокода.
15. Создаётся запись в `user_operations`.
16. Транзакция фиксируется.

Метод отмечен `@Transactional`. Если любой шаг завершится ошибкой, все изменения откатятся.

### Почему нужна блокировка товара

Допустим, на складе осталась одна штука. Два пользователя одновременно нажали «Купить».

Без блокировки оба запроса могли бы увидеть `stock = 1` и оба создать заказ. С `FOR UPDATE` первый запрос блокирует строку товара. Второй ждёт, затем читает уже обновлённый `stock = 0` и получает `INSUFFICIENT_STOCK`.

### Снимок цены

Текущая цена хранится в `products.price`. Цена покупки сохраняется отдельно в `order_items.price_at_order`.

Если товар стоил 100, пользователь оформил заказ, а продавец потом поставил цену 150, старый заказ продолжит показывать цену 100.

### Изменение заказа

Изменять можно только заказ в статусе `CREATED`.

1. Проверяется владелец заказа.
2. Проверяется статус.
3. Проверяется rate limit обновления.
4. Старые остатки возвращаются.
5. Новые товары проверяются и блокируются.
6. Новые остатки резервируются.
7. Сумма пересчитывается.
8. Промокод перепроверяется.
9. Старые позиции заменяются новыми.

Всё происходит в одной транзакции.

### Отмена заказа

Отменить можно заказ в статусе `CREATED` или `PAYMENT_PENDING`.

При отмене:

- товары возвращаются на склад;
- использование промокода уменьшается;
- статус становится `CANCELED`.

### Промокоды

Есть два типа:

- `PERCENTAGE` — процентная скидка;
- `FIXED_AMOUNT` — фиксированная сумма.

Проверяются:

- флаг `active`;
- начало и конец срока действия;
- `current_uses < max_uses`;
- минимальная сумма заказа.

Процентная скидка ограничена 70% суммы. Фиксированная скидка не может сделать итог отрицательным.

## 5. Роли и права

| Операция | USER | SELLER | ADMIN |
|---|---|---|---|
| Смотреть товары | да | да | да |
| Создавать товар | нет | да | да |
| Изменять товар | нет | только свой | любой |
| Архивировать товар | нет | только свой | любой |
| Создавать заказ | да | нет | да |
| Получать заказ | только свой | нет | любой |
| Изменять заказ | только свой | нет | любой |
| Отменять заказ | только свой | нет | любой |
| Создавать промокод | нет | да | да |

Важно различать role check и ownership check.

- Role check отвечает на вопрос: «Такой тип пользователя вообще может выполнять операцию?»
- Ownership check отвечает на вопрос: «Этот конкретный товар или заказ принадлежит пользователю?»

Два продавца имеют одинаковую роль, но один продавец не может изменить товар другого.

## 6. База данных

### `users`

Пользователи: UUID, логин, BCrypt-хеш пароля, роль, время создания.

### `products`

Товары: название, описание, цена, остаток, категория, статус, продавец, даты.

На `status` создан индекс `idx_products_status`, чтобы быстрее фильтровать товары по статусу.

### `orders`

Заказы: пользователь, статус, промокод, итоговая сумма, скидка, даты.

Частичный уникальный индекс запрещает два активных заказа у одного пользователя.

### `order_items`

Позиции заказа: заказ, товар, количество, цена на момент заказа.

### `promo_codes`

Промокоды: код, тип скидки, значение, минимальная сумма, лимит и срок действия.

### `user_operations`

История создания и изменения заказов. Используется для rate limit.

### Почему деньги хранятся не в `double`

В PostgreSQL используется `NUMERIC(12,2)`, а в Java `BigDecimal`. Обычный `double` хранит число приблизительно и может дать результат вроде `0.1 + 0.2 = 0.30000000000000004`. Для денег это нежелательно.

### Автоматические даты

`created_at` получает `CURRENT_TIMESTAMP` при вставке. Для `updated_at` создан PostgreSQL-триггер `set_updated_at`, который обновляет дату перед изменением строки.

## 7. Что делает каждый файл

### Корень проекта

#### `README.md`

Описание архитектуры, возможностей, запуска, демонстрационных запросов и кодогенерации. На защите удобно начать с этого файла.

#### `pom.xml`

Конфигурация Maven. Подключает Spring Boot, Web, Validation, JDBC, Security, PostgreSQL, Flyway, JWT, Swagger и тестовые зависимости. Здесь же настроен OpenAPI Generator.

Главное место в `pom.xml` — плагин `openapi-generator-maven-plugin`. Он читает `api.yaml` и создаёт Java-интерфейсы API и DTO в `target/generated-sources/openapi`.

#### `Dockerfile`

Собирает приложение в два этапа. Сначала Maven создаёт `marketplace.jar`, затем JAR переносится в отдельный образ только с Java Runtime. Это называется multi-stage build: финальный образ не содержит Maven и исходники.

Также внутри Dockerfile есть health-check `/health`.

#### `docker-compose.yml`

Запускает два сервиса:

- `db` — PostgreSQL 16;
- `app` — Java-приложение.

Приложение запускается только после того, как база станет healthy. PostgreSQL снаружи доступен на порту `5433`, приложение — на `8080`.

#### `.gitignore`

Не позволяет загрузить в Git папку `target`, сгенерированный код и настройки IDE.

#### `.dockerignore`

Не копирует в Docker build context ненужные файлы, например `.git`, `target` и `.idea`.

#### `docs/c4-container.puml`

Исходник C4 Container-диаграммы из ДЗ1. Там показана целевая микросервисная архитектура с User, Catalog, Feed, Order, Payment и Notification Service.

В ДЗ2 всё реализовано одним приложением. Это учебное упрощение: требование локальной транзакции между заказом и остатком реализуется проще и надёжнее внутри одного приложения и одной БД.

### Точка входа

#### `Application.java`

Главный класс. Метод `main` запускает Spring Boot. Аннотация `@SpringBootApplication` включает автоконфигурацию и поиск компонентов.

### Папка `api`

Здесь лежат ручные реализации сгенерированных delegate-интерфейсов. Эти классы почти не содержат бизнес-логики.

#### `HealthApiDelegateImpl.java`

Возвращает `200 OK` и `{"status":"ok"}` для `/health`.

#### `AuthApiDelegateImpl.java`

Передаёт регистрацию, вход и refresh в `AuthService`.

#### `ProductsApiDelegateImpl.java`

Передаёт операции товаров в `ProductService`. Для создания возвращает `201`, удаления — `204`.

#### `OrdersApiDelegateImpl.java`

Передаёт создание, получение, изменение и отмену заказа в `OrderService`.

#### `PromoCodesApiDelegateImpl.java`

Передаёт создание промокода в `PromoCodeService`.

### Папка `config`

#### `AppProperties.java`

Типизированно читает настройки с префиксом `app`: JWT-секрет, срок токенов и rate limit.

#### `OpenApiConfig.java`

Публикует `api.yaml` по адресу `/openapi/api.yaml`, чтобы Swagger UI мог открыть именно исходный контракт.

#### `SecurityConfig.java`

Настраивает Spring Security:

- отключает серверную сессию;
- открывает `/health`, `/auth/**`, OpenAPI и Swagger;
- требует JWT для остальных запросов;
- подключает `JwtAuthenticationFilter`;
- создаёт BCrypt-кодировщик паролей;
- настраивает ответы `401` и `403`.

### Папка `domain`

Это внутренние Java-record для строк базы. Они не являются DTO API.

#### `UserRow.java`

Представляет пользователя из базы.

#### `ProductRow.java`

Представляет товар из базы.

#### `OrderRow.java`

Представляет заказ вместе с кодом промокода.

#### `OrderItemRow.java`

Представляет одну позицию заказа и её `priceAtOrder`.

#### `PromoCodeRow.java`

Представляет промокод из базы.

### Папка `service`

#### `AuthService.java`

Регистрация, проверка пароля, вход и обновление токенов. Использует `UserRepository`, BCrypt и `JwtService`.

#### `ProductService.java`

Бизнес-правила товаров: роли, владелец, пагинация, фильтры и мягкое удаление.

#### `OrderService.java`

Главный бизнес-файл. Реализует транзакции заказов, блокировки, остатки, price snapshot, промокоды, rate limit, ownership и расчёт суммы.

#### `PromoCodeService.java`

Проверяет роль создателя, создаёт промокод и превращает запись БД в API-ответ.

### Папка `repository`

#### `UserRepository.java`

SQL для поиска и создания пользователей.

#### `ProductRepository.java`

SQL для CRUD товаров, пагинации, фильтров, изменения stock и блокировки `FOR UPDATE`.

#### `OrderRepository.java`

SQL для заказов и позиций: создание, получение, блокировка, замена позиций и отмена.

#### `PromoCodeRepository.java`

SQL для создания, блокировки и изменения счётчика промокода.

#### `UserOperationRepository.java`

Получает время последней операции и сохраняет новую операцию для rate limit.

### Папка `security`

#### `AuthenticatedUser.java`

Объект текущего пользователя: UUID, логин и роль. Метод `hasRole` упрощает проверку роли.

#### `CurrentUser.java`

Берёт текущего пользователя из Spring Security Context. Если пользователя нет, возвращает `401`.

#### `JwtService.java`

Подписывает и проверяет JWT. В claims записывает `sub`, `username`, `role`, `type`, время выдачи и окончания. Проверяет, что access token нельзя использовать как refresh и наоборот.

#### `JwtAuthenticationFilter.java`

Для каждого запроса читает `Authorization: Bearer ...`, проверяет access token и помещает пользователя в Security Context. Истёкший токен даёт `TOKEN_EXPIRED`, неправильный — `TOKEN_INVALID`.

### Папка `error`

#### `BusinessException.java`

Исключение для ожидаемых бизнес-ошибок. Содержит HTTP-статус, `error_code`, сообщение и `details`.

#### `GlobalExceptionHandler.java`

Глобально ловит исключения и формирует единый `ErrorResponse`. Отдельно обрабатывает бизнес-ошибки, Bean Validation, неправильный JSON, ошибки ограничений базы и неожиданные ошибки.

#### `SecurityErrorWriter.java`

Создаёт такой же JSON-ответ для ошибок уровня Spring Security.

### Папка `logging`

#### `RequestLoggingFilter.java`

Создаёт `request_id`, измеряет время запроса, добавляет заголовок `X-Request-Id` и печатает JSON-лог. Для `POST`, `PUT`, `DELETE` логирует тело, но маскирует поля, содержащие `password` или `token`.

### Папка `resources`

#### `application.yml`

Настройки подключения к PostgreSQL, Flyway, JSON, JWT, времени жизни токенов, rate limit и Swagger. Значения базы и секрет можно заменить переменными окружения.

#### `openapi/api.yaml`

Главный контракт API. Содержит endpoints, DTO, обязательные поля, ограничения, роли в описаниях, JWT-схему и каталог ошибок.

#### `db/migration/V1__init.sql`

Первая Flyway-миграция. Создаёт enum-типы, таблицы, foreign keys, check constraints, индексы и триггеры `updated_at`.

### Папка `target`

Появляется после сборки. Там находятся скомпилированные классы, JAR и сгенерированный OpenAPI-код. Папка не хранится в Git.

## 8. Как требования задания закрыты проектом

### 1. OpenAPI CRUD

В `api.yaml` описаны `POST`, `GET`, `PUT`, `DELETE /products`, пагинация и фильтры.

### 2. Схемы данных

Есть отдельные `ProductCreate`, `ProductUpdate`, `ProductResponse`, enum статусов, `required`, `nullable`, `decimal`, `date-time`.

### 3. Кодогенерация

`pom.xml` генерирует контроллеры и DTO при Maven-сборке. Результат лежит в `target` и игнорируется Git.

### 4. PostgreSQL и CRUD

> В этом домашнем задании я продолжил маркетплейс из ДЗ1 и реализовал contract-first REST API. Стек — Java 21, Spring Boot, PostgreSQL, Flyway, OpenAPI Generator, Spring Security и JWT. Приложение и база запускаются через Docker Compose.
>
> Источником истины для API является файл `src/main/resources/openapi/api.yaml`. В нём описаны endpoints, входные и выходные модели, ограничения валидации, ошибки и JWT security scheme. Контроллеры и DTO я не писал вручную: OpenAPI Generator создаёт их в `target/generated-sources/openapi` во время Maven-сборки. Ручные классы `*ApiDelegateImpl` только соединяют сгенерированный API с сервисным слоем.
>
> Данные хранятся в PostgreSQL. Схема создаётся Flyway-миграцией `V1__init.sql`. Есть таблицы пользователей, товаров, заказов, позиций, промокодов и операций пользователей. На статусе товара есть индекс. Время создания заполняется default-значением, а `updated_at` — триггером. Удаление товара мягкое: строка сохраняется, статус меняется на `ARCHIVED`.
>
> Авторизация построена на JWT. Access token живёт 20 минут, refresh token — 14 дней. Пароли хранятся как BCrypt-хеши. Есть роли USER, SELLER и ADMIN. Продавец может управлять только своими товарами, покупатель — только своими заказами, администратор имеет расширенный доступ.
>
> Самая важная логика находится в `OrderService`. Создание, изменение и отмена заказа выполняются под `@Transactional`. При создании я проверяю rate limit, активный заказ, существование и статус товаров, затем блокирую товары через `SELECT FOR UPDATE`, проверяю остатки, считаю сумму и промокод, уменьшаю stock и сохраняю заказ. Если возникает ошибка, Spring откатывает всю транзакцию.
>
> `SELECT FOR UPDATE` нужен для конкурентных заказов. Если осталось одна штука, два запроса не смогут одновременно успешно её купить. Цена на момент заказа сохраняется в `order_items.price_at_order`, поэтому изменение текущей цены товара не меняет старый заказ.
>
> Ошибки имеют единый формат `error_code`, `message`, `details`. Каждый запрос записывается в JSON-лог с request id, методом, endpoint, статусом, временем выполнения и пользователем. Пароли и токены в логах маскируются. Тот же request id возвращается в заголовке `X-Request-Id`.
>
> В ДЗ1 показана целевая декомпозиция на микросервисы. В ДЗ2 каталог, заказы, пользователи и промокоды реализованы одним учебным приложением, потому что по условию создание заказа и резервирование остатка должны выполняться в одной локальной транзакции.

## 11. Возможные вопросы преподавателя

### Почему OpenAPI-first?

Контракт создаётся до реализации, клиент и сервер заранее согласованы, DTO и контроллеры не дублируются вручную, документация меньше расходится с кодом.

### Где контроллеры?

Они генерируются в `target/generated-sources/openapi`. В Git их нет, потому что сборка должна воспроизводимо создавать их из `api.yaml`.

### Почему есть `domain`-классы, если ручные DTO запрещены?

`ProductRow`, `OrderRow` и другие — не API DTO. Это внутренние представления строк базы. Запросы и ответы API используют только generated model.

### Что делает `@Transactional`?

Открывает транзакцию перед методом. При успехе выполняется commit, при runtime-исключении — rollback.

### Что будет, если ошибка возникнет после уменьшения stock?

Транзакция откатится. Остаток, заказ, позиции и счётчик промокода вернутся к состоянию до запроса.

### Зачем `FOR UPDATE`?

Чтобы два параллельных заказа не продали один и тот же остаток.

### Почему товары блокируются в порядке UUID?

Одинаковый порядок получения нескольких блокировок уменьшает вероятность deadlock.

### Чем 401 отличается от 403?

`401` — пользователь не аутентифицирован или токен неправильный. `403` — пользователь распознан, но у него нет права на операцию.

### Почему пароль не хранится как обычный текст?

При утечке базы обычные пароли сразу станут известны. BCrypt хранит медленный односторонний хеш с солью.

### Почему access и refresh tokens раздельные?

Access короткий и используется для API. Refresh живёт дольше и нужен только для получения новой пары токенов.

### Можно ли отозвать refresh token?

В текущей учебной реализации серверного списка токенов нет. Для production стоило бы хранить хеши refresh token, поддерживать отзыв и rotation reuse detection.

### Почему soft delete?

На товар ссылаются старые заказы. Физическое удаление сломало бы историю или foreign key. Архивирование сохраняет данные.

### Зачем `price_at_order`?

Цена в каталоге меняется, но история покупки должна оставаться неизменной.

### Зачем проверять права в Service, если есть Spring Security?

SecurityConfig проверяет наличие аутентификации. Service знает конкретные бизнес-правила: роль и принадлежность конкретного товара или заказа.

### Как работает rate limit?

В `user_operations` хранится время последней операции нужного типа. Если оно позже текущего времени минус `ORDER_LIMIT_MINUTES`, возвращается `429 ORDER_LIMIT_EXCEEDED`.

### Почему `JdbcTemplate`, а не JPA?

Проект небольшой, а явные SQL-запросы и `FOR UPDATE` важны для задания. `JdbcTemplate` позволяет хорошо видеть SQL и при этом использовать транзакции Spring.

### Почему нельзя использовать `double` для денег?

Он хранит дроби приблизительно. Используются `BigDecimal` и `NUMERIC(12,2)`.

### Для чего нужен индекс по status?

Фильтрация по статусу — частая операция. Индекс позволяет базе не просматривать всю таблицу.

### Зачем проверки и в Java, и в базе?

Java возвращает понятную бизнес-ошибку. Ограничения БД остаются последней защитой целостности при ошибке в коде или конкурентном запросе.

### Что такое Flyway?

Версионирование схемы базы. Flyway хранит применённые миграции в `flyway_schema_history` и выполняет только новые.

### Почему ДЗ1 микросервисное, а ДЗ2 одно приложение?

ДЗ1 — целевая архитектура. ДЗ2 — учебная реализация ограниченного набора функций. Единое приложение позволяет выполнить заказ и резервирование в одной локальной транзакции. При разделении на сервисы потребовались бы Saga, компенсации, идемпотентность и Outbox.

### Что улучшить для production?

- секреты хранить в secret manager;
- добавить хранение и отзыв refresh token;
- structured logging через логгер, а не `System.out`;
- интеграционные тесты с Testcontainers;
- метрики и distributed tracing;
- idempotency key для создания заказа;
- Saga и Outbox при разделении на микросервисы;
- отдельные endpoints переходов оплаты и доставки.
